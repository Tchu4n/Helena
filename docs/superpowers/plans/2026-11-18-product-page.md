# Product page — implementation plan

> **Status:** done, minor review items pending. Translated to English on 2026-11-19. `PRO-12` and `PRO-14` later changed to the card flow (`RestockAlertCard`); the spec is the source of truth.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Have the `/produto/[slug]` page working against the API: photos, price and installments, color, sizes, size guide, shipping by CEP, "Avise-me quando estiver disponível" and "Adicionar à sacola", with the bag counter in the header and tabs.

**Architecture:** The page in `app/` fetches the product and composes three independent blocks: the product details (`catalog`), size choice with the buy button (`catalog`, calling the bag's Server Action received as a prop) and the shipping calculator (`cart`). The bag lives in an `httpOnly` cookie with the bag id in the API; the CEP is kept inside the bag (`setCartCep`), with no cookie of its own. Purchase screens get a route group without bottom tabs (`GER-02`).

**Tech Stack:** Next.js 16.4.6 (App Router, `cacheComponents` on), React 19 (`useActionState`), Tailwind 4, Zod 4, `server-only`, types generated by `openapi-typescript`, `node:test` and Playwright.

**Spec:** `docs/SPEC-CLIENT.md` (sections 3 and 6; `SAC-06` and `SAC-08` only for the cookie and the CEP), `docs/DESIGN.md` (sections 4 and 5, "Product page"), `contract/openapi.yaml` (`getProduct`, `requestRestockAlert`, `quoteProductShipping`, `createCart`, `getCart`, `addItem`, `setCartCep`), `docs/GLOSSARY.md`.

## Global constraints

All the ones from the previous plan (`2026-11-15-shared-layout-and-catalog.md`) apply, with one change and a few additions:

- **Changed:** this plan has `"use client"`, only on three leaves: `ProductPurchase`, `RestockAlertForm` and `ShippingCalculator`. Nothing else.
- A client component gets only objects built by `views.ts` (fields the screen uses). Never the API response, never the bag id.
- Server Action, always in this order: check authorization, validate with Zod, run, invalidate (`refresh()` from `next/cache`). Bag authorization = the id comes **only** from the `httpOnly` cookie, never from the form.
- Values the API already calculates are not recalculated in the front end: installments come from `installmentPlan`, "low stock" comes from `lowStock` (the 15-unit limit belongs to the API), free shipping comes from `free`.
- React 19 clears the form after the action: everything the customer typed comes back in the action state and is used as `defaultValue` (`GER-06`, "nothing the customer typed is lost").
- Before using a Next API, read the guide: `route-groups.md`, `not-found.md`, `refresh.md`, `07-mutating-data.md`, `cookies.md`, `image.md` and, in `08-caching.md`, what applies to a dynamic route with `cacheComponents`. Reading `params`, cookies and the API goes in an async component inside `<Suspense>` (decision from Task 4 of the previous plan).

## Review focus

1. **CEP typed with hyphen or space** (`01310-100`, `01310 100`): counts as `01310100`; only letters or fewer than 8 digits give the `PRO-09` error. Tested in Task 6 (unit).
2. **Our API returns 500 on shipping:** the `GER-06` message shows, the CEP stays in the field and "Adicionar à sacola" keeps working (never block the purchase because of shipping). Tested in Task 6.
3. **Old bag cookie** (the API answers 404 for that id): the item goes into a new bag, with no error on screen. Tested in Task 4.
4. **Odd product address** (`/produto/nao-existe`, `/produto/..%2Fcarts`): the store's 404 page, never a 500 error nor a call to another API route. Tested in Task 3.
5. **Double tap on "Adicionar à sacola"** (the API adds up the quantity): the button is disabled while the action runs, and only one item goes in. Tested in Task 4.

## Not in this plan

- **Bag panel (`SAC-01`)** and **quick buy from the card (`CAT-08`)**: they go to the bag plan. Until then, `PRO-07` shows "Peça adicionada à sacola" and the counter goes up; the panel replaces that message later.
- Announcement bar hidden on bag and checkout (`GER-02`, second line): comes with those screens. On the product screen it stays, as the spec asks.
- `generateMetadata` with product name and photo (Instagram preview): not in the spec; left for when the owner asks.
- The "Finalizar compra" and "Ver sacola" links don't exist on this screen yet.

## Decisions in this plan (approved by the owner on 2026-11-18)

| Subject | Decision |
|---|---|
| Where the `PRO-08` CEP is kept | Inside the bag: calculating shipping creates the bag if it doesn't exist and calls `setCartCep`. That way the only cookies are still the necessary ones from `GER-04`. Rejected alternative: a `helena_cep` cookie, which would be a third cookie |
| Bag cookie | `helena_cart`, value = `id` returned by `createCart`, `httpOnly`, `SameSite=Lax`, `Secure` in production, `path=/`, valid for 30 days (`SAC-06`) |
| Sold-out size chosen | The chip can be tapped (it isn't `disabled`), but the main button is disabled with the text "Esgotado" and "Avise-me quando estiver disponível" shows (`PRO-03`, `PRO-12`, `PRO-14`) |
| `PRO-07` confirmation until the panel exists | Text "Peça adicionada à sacola" in a `role="status"` region |
| `PRO-12` alert channel | Radio "E-mail" / "WhatsApp", with email selected at first (it is the channel for the alert, not marketing consent) |
| New texts | "Escolha um tamanho" (`PRO-05`), "Digite um CEP com 8 números" (`PRO-09`), "Digite um e-mail válido", "Digite o WhatsApp com DDD, só números", "Pronto! Vamos avisar quando o tamanho {T} estiver disponível. Usaremos seu contato só para esse aviso." |
| Route groups | `app/(browse)/` with the tabs (`/`, `/catalogo`, `/buscar`, `/cookies`); `app/(buy)/` without tabs, with room for the fixed button (`/produto/[slug]` now; bag and checkout later). Addresses don't change |
| Gallery | CSS carousel (`snap-x`) on the phone, 2×2 grid from `md` up; no JavaScript; the first photo with `preload` |
